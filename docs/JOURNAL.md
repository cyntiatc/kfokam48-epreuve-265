## Étape 3 — Enveloppe

**Fait :** (en cours) avant l'enveloppe, audit de conformité livré dans le commit de jalon `b5c14fb` : Swagger UI vérifié dans un navigateur, réponse 400 `REQUETE_INVALIDE` ajoutée à `GET /api/tableau` dans le contrat et couverte par le test de conformité, codes `SESSION_DEJA_CLOTUREE` et `ERREUR_INTERNE` ajoutés à la description du schéma `Erreur`, serveur relatif `/` ajouté au contrat pour que « Try it out » fonctionne aussi depuis `127.0.0.1`. Issue #17 (retour client : sur deux émargements quasi simultanés, un seul est enregistré, et une nouvelle tentative réussit) : analyse et rédaction dans `docs/ISSUE_17_BUG_CONCURRENCE.md`. Mécanisme identifié : l'émargement et l'attribution des exercices en attente partagent une transaction ; si deux émargements attribuaient en même temps le même exercice, le second violerait `uk_relectures_exercice` (RG8), renverrait 500 et sa présence serait annulée avec la transaction. Le code est protégé depuis le ticket #4 (commit `4a53803`) par le verrou pessimiste des exercices en attente : le bug n'est pas reproductible. Test de non-régression `PresenceConcurrencyIntegrationTest` : 2 scénarios (sans exercice, avec un exercice en attente) rejoués 20 fois, les deux émargements libérés au même instant ; vert sur le code actuel. Aucun code de production modifié. `mvn clean test` : 130 tests verts, dont 34 d'intégration, aucun ignoré. Reste à faire : l'évolution demandée par le client, deux relecteurs par exercice avec calcul de la moyenne, pas encore commencée ; elle contredit la section 3.2 du cahier des charges (relectures multiples exclues en version 1), RG8 et la contrainte `uk_relectures_exercice`.

**Bloqué :** (durée non mesurée) Swagger UI ne s'affichait pas : la configuration était correcte, mais aucune compilation n'avait eu lieu depuis l'ajout de springdoc (dépendance jamais téléchargée) et PostgreSQL était arrêté. (durée non mesurée) analyse des cas limites de concurrence entre émargement simultané et attribution d'exercices : l'insertion seule ne crée aucun conflit (la contrainte UNIQUE ne porte que sur un même étudiant), le conflit n'existe que lorsqu'un exercice attend un relecteur. (durée non mesurée) la consigne du jury demandait un test de reproduction qui échoue avant tout correctif, mais le bug ne se reproduit pas sur le code actuel : 7 exécutions de 40 émargements simultanés, aucune présence perdue. Pour m'assurer que le test n'était pas aveugle, le verrou a été retiré dans une copie du backend hors dépôt : échec dès la première tentative, avec le symptôme du client. J'ai choisi de garder le test comme test de non-régression plutôt que de réintroduire le bug pour obtenir un test rouge.

**IA :** lui ai demandé l'audit de conformité, la rédaction de l'issue #17 et le test de reproduction. Vérifié : Swagger UI rendu dans Chrome (7 opérations, aucune erreur) et « Try it out » exécuté depuis `127.0.0.1` ; le test de concurrence, dont les deux threads sont libérés ensemble par un `CountDownLatch`, exécuté 7 fois ; contre-épreuve sans le verrou, qui échoue avec `duplicate key value violates unique constraint "uk_relectures_exercice"` ; historique Git consulté pour dater le verrou. Quand le test est resté vert, l'IA a refusé de le faire échouer artificiellement et m'a proposé trois options ; j'ai retenu le test de non-régression. L'IA a aussi relevé deux autres explications à vérifier avec le client (tableau récapitulatif chargé seulement à la demande, identifiant du voisin saisi par erreur) et une concurrence non testée entre dépôt d'exercice et émargement, qui peut laisser un exercice sans relecteur alors qu'un étudiant est présent.
